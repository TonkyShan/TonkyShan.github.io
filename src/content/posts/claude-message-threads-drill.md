Claude API 11 月 2 日上线了一个 beta 功能，叫 message threads。

## 它解决什么问题

写过 Agent 的应该都知道，每调用一次模型，都要把系统提示、工具定义和之前的全部对话重新发一遍。Agent 调一次工具就是一轮，调了几十次之后，每次请求都很大，服务端每次也要把整段对话重新校验、分词一遍。

message threads 的做法是让服务端把对话存起来。第一次请求照常发完整对话，多加一个 `"thread": {"type": "create"}`；之后每一轮只发新增的消息，带上上一轮回复的 id。

它有两个限制。一是最后一次请求之后 5 分钟就过期。二是价格不变，它省的是请求体积和首字延迟，不省 token 钱。

## 在本地模拟

我让 Claude Code 照着官方文档写了一个本地 mock 的 API 服务，把 threads 的规则都实现出来：创建、续接、5 分钟过期、一个 id 只能续接一次、续接时不能再带系统提示和工具。时钟可以手动拨，"过 6 分钟"不用真的等。

然后让官方的 Go SDK 连到这个 mock 上跑。SDK 里有一个专门处理 thread 的辅助对象，过期了会自动重建。这样就能看到它在各种异常情况下具体会发出什么请求。

## 先看省了多少

模拟的是一个读代码的 Agent，系统提示 8 KB 左右，每次 grep 返回 2 KB 多。

| 工具调用次数 | 不用 thread 的总发送量 | 用 thread 的总发送量 | 相差 |
|---|---|---|---|
| 5 | 110 KB | 28 KB | 3.9 倍 |
| 20 | 993 KB | 86 KB | 11.5 倍 |
| 50 | 5.4 MB | 0.2 MB | 26.6 倍 |

不用 thread 的时候，每轮都要重发越来越长的历史，总量按轮数的平方增长；用了 thread 是线性的。服务端要处理的内容也是同样的比例。

这里测的是发送量和处理量，不是延迟。真实的首字延迟能快多少，得调真的 API 才知道，官方的说法是"更低、更稳定"。

## 再看出了问题怎么办

接下来故意制造异常，一共 6 个场景：

| 场景 | SDK 的反应 |
|---|---|
| 等人审批，停了 6 分钟，thread 过期 | 续接收到 404，用本地的完整对话重建，再接着续接 |
| 服务端回答了，但没有存这一轮 | 当时没有任何迹象，下一轮续接才收到 404，然后重建 |
| 同一个 id 已经被别处续接过 | 收到"已续接"的错误，重建 |
| 中途改了系统提示 | 本地直接报错，一个请求都没发 |
| 中途换了模型 | 请求发出去，服务端返回 400，SDK 不处理，交给调用方 |
| 模型拒答 | 不保留被拒的那一轮，下一轮重开一个新 thread |

其中第二个场景值得单独说一下。比如模型生成的工具调用被 max_tokens 截断了，API 照常返回结果，但不会把这一轮存进 thread。返回里没有任何标记，要等下一轮去续接的时候才会收到 404。这次请求成功了，不代表状态已经存下来了。

## SDK 是怎么写的

Go SDK 里处理 thread 的代码只有 654 行，结构不复杂。

它在本地保留一份完整的对话，同时记着其中哪部分已经发给了服务端，每一轮只发两者之间的差。出错的时候只往一个方向降级：先尝试续接；续接不上，就用本地的完整对话重建；重建之后还是找不到，就干脆不用 thread，按普通请求发。只降不升，所以一轮最多发 3 个请求，不会在两种模式之间来回切。

模型拒答、流式输出中途断开、回复来自后备模型，这三种情况下，下一轮会直接重开一个新 thread，因为客户端没法确定服务端到底存了什么。

官方文档里有一句话：Your application stays the source of truth for the conversation。服务端存的东西只是用来加速的，随时可能没了，客户端得能从自己手里的数据重建。

## 什么时候用

连续不停的工具调用循环，轮数越多，收益越大。

如果中间要等人审批、等外部回调，5 分钟一过就得重建，几乎每次都会过期，用了反而多一次往返。另外，它不支持批处理、token 计数和上下文压缩，需要零数据保留的场景也不能用。
